The Uniswap v4 hook is the automation

The merchant defines the recipient, the payout asset, the required amount and the deadline once. After that, the hook turns those instructions into automatic on-chain execution — inside the swap, with nobody to ask.

The payer supplies only the order id. They cannot replace the recipient, the payout asset, the required amount or the deadline.

The hook holds no custody, takes no fee, returns no delta and runs no oracle. It does not wait on a backend to approve the result: it either accepts a valid full settlement or reverts the whole transaction.

What this deployment accepts, exactly

Native ETH in, that chain's configured USDC out. This is not a demo limitation that a different link could route around — the deployed contracts refuse anything else in three separate places, and each refusal has its own named error:

  • ✕An order whose input is a token rather than native ETH is refused where it is created — NativeInputOnly().
  • ✕An order whose payout is not this chain's configured currency is refused at the same point — PayoutCurrencyNotAllowed(address).
  • ✕A pool of any other shape is refused by the hook itself, at beforeInitialize, so the wrong pool can never open under it.

The payout currency is an immutable read once at construction from the chain id, so it cannot be changed after deployment by anyone, including us. Accepting more input tokens and more payout assets is written up as a specification with a red-test matrix (docs/INPUT-POLICY-SPEC.md, docs/PAYOUT-POLICY-SPEC.md) and both documents open by saying they are not implemented. A page that advertised them would be describing a document, not a contract.

One address, four chainsWhere V3 is deployed, and what deployment does and does not prove

V3 is deployed and source-verified on Ethereum Sepolia, Unichain Sepolia, Base Sepolia and Arbitrum Sepolia — the same CREATE2 hook address on every one, each bound to that chain's own Uniswap v4 PoolManager, with the same permission bits encoded in the same address. The complete payment flow has been live-fired on Sepolia; the other three deployments have not yet processed a settlement.

Why Sepolia is the demo chain. It is the one environment where the whole path is evidenced end to end: a configured PoolManager and pool, seeded liquidity, order registration, a Universal Router swap, hook enforcement, a settlement receipt, The Graph indexing it, and the ENSv2 delegation. Every link on this page resolves there.

Why Unichain and the other two. They demonstrate that the hook is deterministically deployable across chains rather than tied to one network. Unichain is the natural production target — it is built around Uniswap's own ecosystem, with lower settlement cost — and Base and Arbitrum broaden where a merchant and their liquidity can sit. Deployment is not a payment, so those three carry the deployed-and-verified rung and nothing above it.

This is availability on four chains, not a cross-chain payment. Each deployment settles on its own chain. No bridge and no messaging protocol is integrated, and none is claimed.
