# V1 — THE RECORD OF THE FIRST SETTLEMENT GENERATION

The immutable, auditable proof of the settlement primitive. This file describes contracts that
are live and will not change. Nothing in it is a plan.

**Source state:** commit `5e1d843`, which tag `live-green` already points at.
**Semantic tag:** `v1.0.0` is **proposed and does not exist yet**; creating it is an owner
action. Until then this release is named `live-green` in every claim.
**Documentation HEAD** is whatever commit you are reading this at, and is normally later. The
two are not the same thing and this file never conflates them.

## Why `5e1d843` is the boundary

Three facts, each re-checkable in one command:

| Fact | Command | Result |
|---|---|---|
| `src/` did not change after the release | `git diff --stat live-green..HEAD -- src/` | prints nothing |
| `test/` did not change after the release | `git diff --stat live-green..HEAD -- test/` | prints nothing |
| the live verifier did not change | `git diff --stat live-green..HEAD -- docs/proof/verify-live.sh` | prints nothing |

So the implementation boundary and the proof boundary are the same commit. The commits after it
are documentation, scripts, the web surface, indexer tooling and partner feedback; none of them
touched a contract or a test. `git rev-list --count live-green..HEAD` counts them.

The deployed bytecode was built from `deploy-candidate-4` and the settlement was run from
`deploy-candidate-5`; only the settle stage's deadline constant changed between them, and it
lives in `script/`, not `src/`. `git diff deploy-candidate-5 live-green -- src/` prints nothing,
which is why one source state covers the whole release.

## What V1 proves, stated once and not strengthened

Native ETH input is atomically exchanged through Uniswap v4 into USDC for an order-registered
recipient, with order-bound full-fill enforcement, replay protection, and one indexable receipt.
The executor ends the transaction holding nothing.

The public sentence, used verbatim wherever the live release is described:

> UNICA demonstrates a live, verified USDC settlement flow on Uniswap v4 Sepolia, with
> order-bound full-fill enforcement and an indexable receipt.

## Limitations of V1 — the full list

1. **One input currency.** Native ETH. No ERC-20 payer asset, no Permit2 path.
2. **One payout currency.** USDC, compiled into the contract for this chain. A merchant cannot
   choose what it is paid in.
3. **One chain.** Ethereum Sepolia. The payout table is compiled into the hook and the
   executor's creation code is embedded in the hook's, so changing either moves both addresses
   and the pool id.
4. **Exact-input only.** The hook refuses an exact-output swap in either direction, so an
   invoice denominated in the payout asset cannot be expressed as an order.
5. **No merchant identity or configuration.** The recipient is a raw address supplied at order
   creation. Nothing resolves a name, and nothing is committed about the merchant.
6. **Thin liquidity.** The pool was seeded from what the deployer held. It is a demonstration
   pool, not a market.
7. **Unaudited.** Two independent audits exist for Uniswap's own permissioned-pool work; none of
   that assurance transfers to this repository.
8. **One settlement.** `receiptCount` is 1. The path is proven to work, not proven under load.
9. **The first settlement attempt failed on chain** with `DeadlineInPast`, and that failure is
   recorded rather than hidden. Cause and fix in `docs/DEPLOYMENT.md`.

## What may never be done to this release

The contracts, the deployed addresses, the pool, `broadcast/`, `docs/proof/`, the live subgraph
manifest and every existing tag are frozen. A later generation is a new contract generation
beside them with its own addresses, ABI, proof namespace and documentation — never an overwrite
of these, and never a repointing of this evidence at something else.
