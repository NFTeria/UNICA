# x402 on Arc — official facts, and what they mean for UNICA

Every row is either **official** (a quote or JSON path from a named primary source) or **analysis**
(reasoning built from those facts, applied to UNICA's own contracts). Repository notes elsewhere in
this tree (`docs/ARC-FACTS.md`, `integrations/arc-treasury/`, `docs/unica-v4/evidence/`,
`docs/unica-v4/DECISIONS.md`) are **leads only** — nothing from them is repeated here without
independent primary-source confirmation. Retrieved **2026-09-11**.

Primary sources used: `github.com/coinbase/x402` / `github.com/x402-foundation/x402` (the x402
specification, now canonical under the x402 Foundation), `docs.x402.org`, `docs.cdp.coinbase.com/x402`,
`developers.circle.com`, `docs.arc.io`, `docs.privy.io`. Third-party summaries (Eco, SKALE, DWF Labs,
Medium, etc.) are named explicitly wherever used and are never the sole source for a load-bearing
claim.

## 1. What x402 is, in its own words

> "x402 is an open standard for internet native payments. It aims to support all networks (both
> crypto & fiat) and forms of value (stablecoins, tokens, fiat)." — `README.md`,
> `github.com/coinbase/x402`

The repository itself carries this notice as of retrieval:

> "We've moved the x402 repo under the x402 Foundation repo. All issues and PRs were transferred
> here: `github.com/x402-foundation/x402`. Our repo (`coinbase/x402`) is now a development fork." —
> `README.md`, `github.com/coinbase/x402`

So the canonical repository is **`x402-foundation/x402`**; `coinbase/x402` still mirrors the same
content but is described, in its own README, as a fork. Both were fetched for this document and
agree on every fact below.

**What x402 is:** a payment **negotiation protocol** built on the unused HTTP `402 Payment Required`
status code. It standardizes *how* a server states a price and *how* a client proves it paid; it
does not itself move money.

> "x402 is not a payment system itself — it is a negotiation protocol that is agnostic to how
> payments are constructed, verified, or settled." — `developers.circle.com/gateway/nanopayments/concepts/x402`

**What x402 is not, by its own stated principles** (`README.md`):
- Not a single-vendor system — "It will never force reliance on a single party."
- Not fiat-first — it "may extend support to fiat based networks, but will never deprioritize
  onchain payments in favor of fiat payments."
- Not custodial — schemes "must not allow for the facilitator or resource server to move funds,
  other than in accordance with client intentions."
- Not a wallet, a swap engine, an escrow, or a pricing oracle. It carries a price and a proof of
  payment; it has no concept of currency conversion (§10 below).

## 3. Roles and the payment flow

Three roles, defined identically in `README.md` and `specs/x402-specification-v2.md`:

| Role | Definition (spec) | Circle's terms for the same role |
|---|---|---|
| **Client** | "Any application or agent that requests access to protected resources" | Buyer |
| **Resource Server** | "A service that requires payment for access to protected resources" | Seller |
| **Facilitator** | "A service that handles payment verification and blockchain settlement" | (same) |

The facilitator never custodies funds:

> "The facilitator does not hold funds or act as a custodian — it performs verification and
> execution of onchain transactions based on signed payloads provided by clients." —
> `docs.x402.org/core-concepts/facilitator`

**The 12-step flow** (`README.md`, "Typical x402 flow"; steps 1–2 are skippable if the client
already knows the price):

1. Client → Resource Server: plain HTTP request.
2. Resource Server → Client: `402 Payment Required` with a base64 `PaymentRequired` object in the
   `PAYMENT-REQUIRED` header.
3. Client picks one `PaymentRequirements` entry from `accepts[]` and builds a `PaymentPayload` for
   its `scheme`/`network`.
4. Client → Resource Server: the same request again, now carrying `PAYMENT-SIGNATURE` (base64
   `PaymentPayload`).
5. Resource Server verifies the payload — locally, or by `POST`ing it to a facilitator's `/verify`.
6. Facilitator → Resource Server: `VerifyResponse` (`isValid`, `payer`, optional `invalidReason`).
7. If invalid, Resource Server returns `402` again with an error. If valid, it proceeds.
8. Resource Server settles — directly on-chain, or by `POST`ing to a facilitator's `/settle`.
9. Facilitator broadcasts the transaction to the chain named in `PaymentRequirements.network`.
10. Facilitator waits for confirmation.
11. Facilitator → Resource Server: `SettlementResponse` (`success`, `transaction`, `network`,
    `payer`).
12. Resource Server → Client: `200 OK` with the resource body and a `PAYMENT-RESPONSE` header
    carrying the base64 `SettlementResponse`.

Three headers carry the entire protocol over HTTP (`specs/transports-v2/http.md`); everything else
in the HTTP response/request body is a normal application concern, untouched by x402:

| Header | Direction | Carries |
|---|---|---|
| `PAYMENT-REQUIRED` | server → client | base64 `PaymentRequired` |
| `PAYMENT-SIGNATURE` | client → server | base64 `PaymentPayload` |
| `PAYMENT-RESPONSE` | server → client | base64 `SettlementResponse` |

(v1 used differently-named headers and a JSON-body 402 response; v2 moved everything to headers so
the response body stays free for the resource itself.)

## 4. Facilitator interface

`specs/x402-specification-v2.md` §7 defines three REST endpoints any facilitator exposes:

- **`POST /verify`** — validates a `{paymentPayload, paymentRequirements}` pair without touching
  the chain. Returns `{isValid, payer, invalidReason?}`.
- **`POST /settle`** — same request shape, but broadcasts. Returns `{success, transaction, network,
  payer, errorReason?}` (`transaction` is `""` on failure).
- **`GET /supported`** — returns every `(x402Version, scheme, network)` triple the facilitator
  handles, plus its `signers` (the addresses it broadcasts from) and any `extensions` it implements.

A resource server is **not required** to use a facilitator at all:

> "The documentation explicitly states facilitators are optional, though recommended. Servers can
> alternatively implement verification and settlement locally." — `docs.x402.org/core-concepts/facilitator`
> (self-facilitation path)

> "It is permissionless — anyone can run a facilitator." — `docs.x402.org/faq`

**Fee model.** The protocol itself charges nothing; fees are a facilitator-operator choice.

> "Gas paid onchain; many facilitators offer zero facilitator fees." — `docs.x402.org/faq`

The Coinbase-run CDP Facilitator is one concrete example, not a protocol rule:

> "The CDP Facilitator charges $0.001 per transaction after the first 1,000 monthly transactions.
> Only successful settlements count as billable transactions; verification and failed settlements
> are free." — `docs.cdp.coinbase.com/x402/support/faq`

## 5. Payment schemes — how money actually moves

A **scheme** is "a logical way of moving money" (`README.md`); each scheme has per-network bindings.
Three exist at retrieval.

### 5.1 `exact` — pay a specific amount, once

`specs/schemes/exact/scheme_exact_evm.md` defines three `assetTransferMethod` options for EVM. All
three are gasless for the payer and none let the facilitator change the amount or destination:

| Method | Mechanism | Gas payer | Use case |
|---|---|---|---|
| **`eip3009`** (recommended) | Token's own `transferWithAuthorization` | Facilitator | Tokens that implement EIP-3009 natively (USDC) |
| **`permit2`** (universal fallback) | Uniswap Permit2's `permitWitnessTransferFrom`, via a canonical `x402ExactPermit2Proxy` at `0x402085c248EeA27D92E8b30b2C58ed07f9E20001` | Facilitator (settlement); payer or a sponsoring extension (one-time Permit2 allowance) | Any ERC-20, including tokens with no native gasless-transfer support |
| **`ERC-7710`** | Smart-account delegation; facilitator calls `delegationManager.redeemDelegations(...)` with `executionCallData` built as a plain `transfer(payTo, amount)` | Facilitator | ERC-4337 / ERC-7579 smart accounts with an active delegation |

**EIP-3009 payload** (`authorization`): `from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`
(32-byte, random) — six fields, signed once via EIP-712, consumed once. This is the flat shape that
matters for §8 below: nothing about a merchant's order terms is inside it.

**Permit2 payload** binds the recipient through a `witness` object: `{to, validAfter}`, hashed into
the EIP-712 digest the payer signs. The `x402ExactPermit2Proxy` enforces the witness — "This Proxy
enforces that funds are only sent to the `witness.to` address" — so a relayer cannot redirect funds,
but the witness is still just one recipient address and a timestamp; no other order metadata is
bound.

**Verification steps** (`specs/x402-specification-v2.md` §6.1.2), run by the facilitator before
settlement: signature validity → payer balance → amount matches exactly → time window valid →
authorization parameters match `PaymentRequirements` → transaction is **simulated** before broadcast.

### 5.2 `upto` — pay up to a ceiling, settle the metered actual

`specs/schemes/upto/scheme_upto.md` — for usage-based pricing (LLM tokens generated, bytes
transferred). Five MUST properties: single-use, time-bound, recipient-bound, settled amount `<=`
authorized max, and the same `PaymentRequirements.amount` field is **phase-dependent** — it means
"ceiling" at `/verify` and "actual charge" at `/settle`. Explicitly out of scope: multi-settlement
streaming, recurring charges, and open-ended allowances.

### 5.3 `batch-settlement` — defer on-chain finality

`specs/schemes/batch-settlement/batch_settlement.md` — for volumes where per-request on-chain gas or
latency is uneconomic. `/settle` no longer broadcasts a transaction; it validates the commitment and
returns a **commitment identifier** (a voucher, channel receipt, or ledger reference) instead of a
transaction hash. Two trust models a network binding may choose:

- **Capital-backed**: the client's own pre-funded escrow or payment channel backs the commitment; no
  intermediary underwrites it.
- **Credit-backed**: a network intermediary underwrites the commitment against a billing identity,
  and settles off-chain on its own schedule.

This is the scheme behind Circle's Gateway "nanopayments" product (§9) — Gateway batches many
EIP-3009 authorizations and nets them into one on-chain settlement, paying gas once per batch instead
of once per payment.

## 6. Auth flow, signing, and wallets

Every scheme signs with **EIP-712 typed data**, never a raw transaction:

> "x402 payments are signed as EIP-712 typed data, not as ordinary transactions... standard
> transaction policies don't apply." — `docs.privy.io/recipes/agent-integrations/x402`

This is also why an agent needs a **programmatic wallet**, not gas:

> "Programmatic wallets (e.g., CDP Wallet API, viem, ethers-v6 HD wallets) let agents sign EIP-712
> payloads without exposing seed phrases." — `docs.x402.org/faq`

> "The facilitator pays network gas for settlement transactions. Buyers using EIP-3009 tokens (like
> USDC) sign authorizations rather than transactions, avoiding gas token requirements. For other
> ERC-20s via Permit2, the facilitator sponsors the one-time approval only for tokens implementing
> EIP-2612." — `docs.cdp.coinbase.com/x402/support/faq`

**Authenticated pricing.** The core spec allows — but does not mandate — wiring an identity layer in
front of the price:

> "The protocol supports integration with authentication systems (e.g., Sign-In with Ethereum) to
> enable authenticated pricing models where verified users receive discounted rates." —
> `specs/x402-specification-v2.md` §10.2

There is no browser-chrome requirement anywhere in the spec: the entire protocol lives in three HTTP
headers, so any HTTP client — `curl`, `axios`, `httpx`, an MCP tool call, an A2A agent message — can
speak it. Privy's own integration is the concrete "browser + wallet" case (§10).

## 7. Finality, replay, idempotency, refunds, receipts

**Finality.** The base `exact`/`upto` path is synchronous: `/settle` broadcasts and waits, and the
`SettlementResponse.transaction` hash is the finality evidence (`specs/x402-specification-v2.md`
§5.3). The CDP Facilitator adds an operational state the core spec does not define:

> "A `settlement_pending` response means the transaction was broadcast but didn't confirm within the
> synchronous window — it's not a failed payment. Reconcile the returned transaction instead of
> retrying." — `docs.cdp.coinbase.com/x402/support/faq`

This is a **facilitator-specific behavior**, not a core-protocol error code — it does not appear in
the thirteen `invalid_*`/`unexpected_*` codes the spec itself defines (§8 below). Any UNICA
integration must treat "pending" as facilitator-defined, not standardized.

**Replay protection**, per `specs/x402-specification-v2.md` §10.1: a fresh 32-byte nonce per
authorization; the token contract itself refuses nonce reuse at the EIP-3009/Permit2 level (not just
the facilitator); an explicit `validAfter`/`validBefore` (or `deadline`) window bounds how long a
signed authorization is dangerous; and the whole authorization is signed, so it cannot be altered in
flight. The `upto` scheme adds a MUST: "Each authorization MUST be settled at most once" — the
authorization, not just the token-level nonce, is single-use by protocol rule.

**Idempotency** is an optional extension, not core protocol:

> `specs/extensions/payment_identifier.md` — the client attaches an `id` (16–128 chars) inside
> `extensions["payment-identifier"]`. Behavior table from that spec:

| Scenario | Server response |
|---|---|
| New `id` | Process normally |
| Same `id`, same payload | Return cached response |
| Same `id`, different payload | `409 Conflict` |
| Server requires an `id` and none is sent | `400 Bad Request` |

Both the resource server and the facilitator "consume `PaymentPayload`", so either — or both — may
enforce this key. Without the extension, x402's only anti-duplication guarantee is the nonce-level
replay protection above: nothing stops a client from *authorizing* a second, distinct payment for the
same logical request if it retries without reusing the `id`.

**Refunds.** `exact` is defined as irreversible:

> "The `exact` scheme is a push payment — irreversible once executed." — `docs.x402.org/faq`

There is no chargeback, and none is wanted:

> "Since x402 payments are irreversible once settled, chargebacks don't exist — protecting sellers
> from fraud reversals. To refund a buyer, you send a transfer back from your receiving address to
> their original payment address." — `docs.cdp.coinbase.com/x402/support/faq`

`batch-settlement` is the one scheme with a cooperative-refund path built in, via its escrow
redemption step, per the same FAQ.

**Receipts and reconciliation.** The base protocol's only receipt is the `SettlementResponse`
carried in `PAYMENT-RESPONSE` — a transaction hash, network, payer, and success flag. For anything
stronger, `specs/extensions/extension-offer-and-receipt.md` defines a signed-receipt extension:

- **Signed offer** — the resource server can EIP-712- or JWS-sign the terms in each `accepts[]`
  entry, so the price quote itself becomes non-repudiable.
- **Signed receipt** — returned only on success, in `SettlementResponse.extensions["offer-receipt"]`.
  Fields: `version`, `network` (CAIP-2), `resourceUrl`, `payer`, `issuedAt`, and an **optional**
  `transaction`. The spec calls this **privacy-minimal by default**: "intentionally omits transaction
  references to reduce correlation risk," and a server includes `transaction` only when it wants
  stronger on-chain verifiability instead.

For plain accounting without the extension, the CDP FAQ's practical answer is to record the
`PAYMENT-RESPONSE` transaction hash "in lifecycle hooks like `onAfterSettle`" — i.e., reconciliation
is a resource-server responsibility, not something x402 automates.

## 8. Error codes and server requirements

`specs/x402-specification-v2.md` §9 defines the protocol's standard error codes (a subset relevant to
UNICA): `insufficient_funds`, `invalid_exact_evm_payload_authorization_valid_after` /
`_valid_before` (expired or not-yet-valid authorization — this is the **expired-quote** case in §16),
`invalid_exact_evm_payload_authorization_value_mismatch`, `invalid_exact_evm_payload_signature`,
`invalid_exact_evm_payload_recipient_mismatch`, `invalid_network`, `invalid_scheme`,
`unsupported_scheme`, `invalid_x402_version`, `invalid_transaction_state`,
`unexpected_verify_error`, `unexpected_settle_error`. Nothing in this list is oracle-shaped — x402
has no price-feed concept, so a "stale oracle" failure (§16) is never an x402 error; it is whatever
error UNICA's own settlement contract raises before x402 is ever reached.

**Server requirements** are deliberately minimal — the stated technical goal is "1 line for the
server, 1 function for the client" (`README.md`). A resource server needs to: return `402` with a
`PAYMENT-REQUIRED` header when unpaid; verify an incoming `PAYMENT-SIGNATURE` (locally or via a
facilitator's `/verify`); settle (directly or via `/settle`); and echo `PAYMENT-RESPONSE` on success.
Reference middleware exists for Express, FastAPI/Flask, Hono, and Next.js (`README.md` §"Server
Frameworks"). It does **not** require TLS, a specific web framework, a database, or any blockchain
node of its own if a facilitator is used — that is the entire point of the facilitator role.

## 9. Supported networks, and where Arc stands

The canonical, actively maintained list is `docs.x402.org/core-concepts/network-and-token-support`.
At retrieval it names dozens of chains — Base, Base Sepolia, Ethereum, Avalanche C-Chain, Polygon,
Arbitrum (One and Sepolia), Solana (mainnet and devnet), Monad, Stable, MegaETH, Mezo, Radius, ADI
Chain, HPP, XDC, Igra, Flare, Celo, Sei, TON, Algorand, Stellar, Aptos, Hedera, Keeta, NEAR,
Concordium, XRPL, Cardano — and states the token-authorization split: "EIP-3009 is preferred when
available (simpler, no approval step). Permit2 serves as the universal fallback."

**Arc does not appear on that list.** Nor does it appear in `specs/x402-specification-v2.md` §11.1's
own worked network-identifier examples (Base Sepolia, Base mainnet, Avalanche Fuji, Avalanche
mainnet, Solana mainnet, Solana devnet). Nor is it among the CDP Facilitator's supported networks:

> "The facilitator supports these chains — Mainnet: Base, Polygon, Arbitrum, World, and Solana.
> Testnet: Base Sepolia, World Sepolia, and Solana Devnet." — `docs.cdp.coinbase.com/x402/core-concepts/facilitator`
> and `docs.cdp.coinbase.com/x402/network-support`

So: **the x402 protocol's own canonical network registry and the largest production facilitator
(Coinbase's CDP Facilitator) do not list Arc, at all, as of this retrieval.** What does exist:

- **`github.com/circlefin/arc-nanopayments`** — Circle's own sample app, description: "demonstrates
  gasless USDC nanopayments using Circle Nanopayments on Arc." A LangChain buyer agent and a
  Next.js seller with x402-protected endpoints. This is a **Circle-published sample repository**, not
  an entry in x402's network registry and not a statement that any production facilitator serves Arc.
- **Circle Gateway** (`developers.circle.com/gateway/references/supported-blockchains`) lists "Arc
  (testnet only)" among 13 supported chains, with nanopayments supported on all of them except
  Solana. Gateway's nanopayments primitive *is* x402's `batch-settlement` model (§5.3), operated by
  Circle as the credit/capital-backing intermediary — but this is Circle's own product wrapping x402,
  run on Circle's own infrastructure, not the open x402 facilitator ecosystem adding Arc support.
- Circle's own blog post on the topic frames Arc as the **settlement environment**, and x402 as the
  **payment-negotiation layer sitting on top of it** — it does not claim Arc is in x402's official
  network list: "x402 protocol for HTTP 402 based payment negotiation" paired with "Arc provides a
  stablecoin-native settlement environment." — `circle.com/blog/build-agentic-systems-for-high-frequency-sub-cent-transactions`

**Verdict: Arc is not officially supported by the x402 protocol or its reference facilitator as of
2026-09-11.** It is supported, testnet-only, by Circle's own Gateway/nanopayments product and
demonstrated in Circle's own sample repository — both Circle-operated, both distinct from the
open x402 ecosystem's network registry. Any UNICA claim that "x402 runs on Arc" must name Circle's
Gateway/nanopayments product specifically, never the generic x402 protocol or the CDP Facilitator.

**Arc network facts used above** (official, `docs.arc.io`, retrieved 2026-09-11): Testnet chain ID
**5042002** (`docs.arc.io/arc/references/connect-to-arc`, and embedded directly in that page's own
client-side wallet-connect script as `const ARC_TESTNET_CHAIN_ID = 5042002`); USDC ERC-20 interface
`0x3600000000000000000000000000000000000000` ("Optional ERC-20 interface for interacting with the
native USDC balance. Uses 6 decimals"); EURC `0x89B50855Aa3bE2F677cD6303Cec089B5F319D72a` ("Main
EURC token contract. Uses 6 decimals") — both from `docs.arc.io/arc/references/contract-addresses`.
Arc mainnet has **no official chain ID or address page yet** at retrieval — `docs.arc.io` documents
Testnet only (page `dateModified: 2026-09-10`); third-party trackers (Chainlist, TrustSwap) report a
mainnet chain ID of `5042` and a September 16, 2026 launch date, but that is **not yet confirmed by

`docs.arc.io` publishes it.

## 10. EURC, BTC-shaped assets, Privy, and gas sponsorship

**EURC.** Circle's own EURC contract on Arc Testnet is confirmed above (6 decimals). Whether EURC
implements EIP-3009 `transferWithAuthorization` the same way USDC does is **reported but not
independently confirmed here**: multiple secondary sources (Eco's support docs, general x402
commentary) state EURC uses the same EIP-3009 path as USDC, but no Circle-published EURC-specific
document or on-chain selector check confirmed it directly as of 2026-09-11. Treat "EURC is
EIP-3009-gasless like USDC" as **plausible, sourced only to non-primary commentary** — verify against
the deployed EURC bytecode before UNICA relies on it. If EURC turns out not to support EIP-3009, the
`permit2` fallback (§5.1) still applies to any ERC-20.

**BTC-shaped assets (cbBTC, wrapped BTC, etc.).** x402's `exact` scheme has no currency-conversion
concept at all — the client pays the exact `asset`/`amount` the server listed in `accepts[]`, in that
same asset. There is no "pay in BTC, settle in USDC" scheme anywhere in the spec. A wrapped-BTC token
would move through x402 only as a `permit2` (or, if it happens to implement EIP-3009, `eip3009`)
transfer of that exact token to `payTo` — full stop. **Any BTC→USDC conversion is necessarily outside
x402 and must be UNICA's own job** (§11).

**Privy.** Officially supported, not a third-party wrapper:

> "Privy offers native x402 support... `useX402Fetch` (React, v3.7.0+) and `createX402Client`
> (Node.js)... Users need USDC in their Privy embedded wallet on the correct network (e.g. Base, Base
> Sepolia, or Solana)." — `docs.privy.io/recipes/agent-integrations/x402`

Arc is **not** among the networks Privy's own x402 doc names. A load-bearing caution from that same
page: because x402 signs EIP-712 typed data rather than ordinary transactions, "standard transaction
policies don't apply" — an embedded-wallet spending-policy engine built around transaction
allowlisting will not automatically catch a malicious x402 authorization; recipient screening has to
happen at the signing-request layer instead.

**Gas sponsorship**, recap with an Arc-specific hazard added: the facilitator always pays the
settlement gas for `eip3009` and for `permit2` after the one-time approval (§4, §6). On Arc
specifically, gas is paid in **native USDC at 18 decimals**, while the ERC-20 USDC interface an
`eip3009`/`permit2` transfer would move is **6 decimals on the same underlying balance**
(`docs.arc.io/arc/references/contract-addresses`: "avoid mixing these values directly, as doing so
may result in incorrect balance handling"). A facilitator naively reusing Base/Ethereum gas-accounting
code on Arc would be exposed to exactly this mismatch — one more reason no production facilitator
lists Arc today (§9).

## 11. Analysis for UNICA (not an x402-spec fact — reasoning applied to this repository's contracts)

**Can x402 carry a payer-bound UNICA order without reproducing Advisory 001?** Not out of the box,
and the reason is structural, not incidental. `docs/v2/SECURITY-ADVISORY-001.md` (this repository)
found that UNICA's own `v2.0.0-rc1` Permit2 witness bound only the payer's half of a quote —
`{quoteId, payer, tokenIn, maxIn, destination, executor}` — leaving the merchant's half (`recipient`,
`merchantSigner`, `tokenOut`, `amountOut`, `pool`, `hook`, `deadline`, ...) unbound and therefore
substitutable by whoever submits `settle()`. x402's own `exact`/EIP-3009 authorization is *narrower
still*: `{from, to, value, validAfter, validBefore, nonce}` — six flat fields, one recipient address,
no quote digest, no merchant identity, no output-asset or output-amount field at all
(`specs/x402-specification-v2.md` §6.1.1). The `permit2` method's `witness` (§5.1) binds one more
field — `to` — but that is exactly the field Advisory 001 shows is insufficient alone: two quotes
differing only in `recipient` and `merchantSigner` produced a byte-identical payer digest in UNICA's
own executor, and a bare `{to, validAfter}` witness has no room to bind more than one of those two
fields. **Wiring x402's stock `exact` scheme straight into a UNICA order would reproduce the exact
failure mode Advisory 001 already found, one layer higher in the stack.** The fix Advisory 001
recommends — hash the full EIP-712 quote digest into the payer's signed witness — has a direct x402
analogue: a UNICA-specific network binding (or an x402 extension) whose signed `payload` is the
*entire* UNICA quote digest, not a flat `to` address, so a relayer cannot substitute a different
order under the same payer signature. That binding does not exist in the x402 spec today; it would be
new UNICA-authored work, and it would need the same adversarial re-derivation Advisory 001 used
before it is trusted.

**Can x402 enable safe public payment links without reproducing Advisory 001?** Only if the *link
itself* carries the full order commitment, not just a destination address. `docs/unica-v4/DECISIONS.md`
records UNICA's own ruling on this class of feature: "Order creation is restricted to approved
merchants or approved checkout creators. Every order binds an explicitly named payer, unless a
separately designed public payment-link mode exists with its own caps and replay protections. Only
the bound payer may settle a payer-bound order. `WrongPayer` is preserved." A public x402 payment
link that simply advertises `accepts[{scheme, network, amount, asset, payTo}]` for an *unbound* payer
is safe **in x402's own terms** — nothing in `PaymentRequirements` claims to name a specific payer,
so there is no `WrongPayer`-shaped promise being broken. It becomes unsafe the moment UNICA tries to
retrofit payer-binding onto it after the fact, because (as above) x402's `exact` authorization has no
field to carry that binding. The safe design is: a public link is an **unbound** UNICA order (its own
supported mode per `DECISIONS.md` #111) with its own caps and replay protections, paid via plain x402
`exact` — not a payer-bound order wearing an x402 wrapper.

**Can x402 call a UNICA settlement contract directly?** No. Every settlement path the spec defines
performs a **flat token transfer to a single address** and nothing else: `eip3009` calls
`token.transferWithAuthorization(...)`; `permit2` calls the canonical proxy's `settle()`, which itself
only executes `permitWitnessTransferFrom` to `witness.to`; and `ERC-7710`'s `executionCallData` is
explicitly constructed as `transfer(payTo, amount)` — "constructs the `executionCallData` encoding an
ERC-20 `transfer(payTo, amount)` call for the required payment" (`specs/schemes/exact/scheme_exact_evm.md`
§3). None of the three carries arbitrary calldata to invoke a custom function like UNICA's
`executor.pay(orderId)`. So pointing `payTo` at a UNICA executor's address would land tokens on that
contract without ever calling its settlement entrypoint — the executor would not know an order had
been paid. Making x402 settlement actually *complete* a UNICA order requires either (a) a UNICA-authored
network binding/extension whose settlement step is "call `pay(orderId)`", not "transfer tokens" — new
work, not present in the spec — or (b) treating x402 purely as the payment-collection leg, with a
separate, UNICA-controlled step (the resource server itself, or a keeper) verifying the x402 receipt
and then invoking UNICA settlement on its own signed order data.

**Recommendation.** Use x402 as the **authorization/collection layer for the leg it is actually good
at — moving an exact, named asset from a client to an address, gaslessly, with a standard HTTP
negotiation — and let UNICA own conversion and order settlement**, for three converging reasons: (1)
x402 has no conversion concept (§10), so any BTC-in/USDC-out or EURC-in/USDC-out flow needs a
converter regardless of what collects the payment; (2) x402's authorization payload cannot carry
UNICA's order-binding fields without new, UNICA-authored extension work, so today it cannot safely
*replace* UNICA's own payer-bound settlement logic (§ above); and (3) it can safely *front* that
logic — collect a same-asset or foreign-asset payment into a UNICA-controlled address under a
standard, widely-supported HTTP mechanism agents already speak, then hand off to UNICA's existing
quote/settle/hook path for anything requiring conversion, order binding, or `WrongPayer` protection.
**Bypass x402 only for the one case §"UNICA context" already rules on: a same-asset USDC payment that
needs no conversion is never forced through a swap** — that principle extends naturally to saying it
should not be forced through an extra x402 round-trip either, if the resource server can accept a
direct, already-payer-bound UNICA order settlement instead. x402 is additive reach (any HTTP agent,
any wallet with USDC), not a replacement for UNICA's settlement guarantees.

## 12. Sequence diagrams

All seven are built strictly from the mechanics verified above (§3–§9); none depict a feature this
document has not sourced. `RS` = UNICA resource server, `Fac` = facilitator, `Chain` = the settlement
network.

**12.1 — USDC pays for an API request (`exact` / `eip3009`, the baseline case)**

```
Client  Client->RS: GET /resource
        RS->Client: 402 + PAYMENT-REQUIRED {exact, eip155:8453, USDC, payTo, amount}
        Client->RS: GET /resource + PAYMENT-SIGNATURE {eip3009 auth, sig}
        RS->Fac: POST /verify {payload, requirements}
        Fac->RS: {isValid:true, payer}
        RS->Fac: POST /settle {payload, requirements}
        Fac->Chain: token.transferWithAuthorization(from,to,value,...)
        Chain->Fac: tx confirmed
        Fac->RS: {success:true, transaction, network, payer}
        RS->Client: 200 OK + PAYMENT-RESPONSE {settlement}
```

**12.2 — EURC paid, USDC received (x402 collects; UNICA converts)**

```
Client  Client->RS: GET /resource   (price quoted in USDC; client only holds EURC)
        RS->Client: 402 + PAYMENT-REQUIRED {exact, EURC, payTo=UNICA-controlled address}
        Client->RS: PAYMENT-SIGNATURE {eip3009-or-permit2 auth over EURC}
        RS->Fac: /verify -> /settle   (x402's job ends here: EURC has moved, exactly as authorized)
        Fac->Chain: settle EURC transfer
        Chain->Fac: tx confirmed (EURC received at UNICA address)
        RS->UNICA: hand off received EURC to UNICA's own quote/settle path
        UNICA->Chain: UNICA-authored conversion (its own pool/hook, NOT an x402 scheme)
        UNICA->RS: USDC delivered to merchant, UNICA order marked settled
        RS->Client: 200 OK + PAYMENT-RESPONSE (x402 receipt) + UNICA order receipt
```

**12.3 — BTC-shaped asset paid, USDC received (Permit2 leg + UNICA conversion)**

```
Client  Client->RS: GET /resource   (client holds a wrapped-BTC ERC-20, no EIP-3009)
        RS->Client: 402 + PAYMENT-REQUIRED {exact, assetTransferMethod:"permit2", wBTC, payTo=UNICA}
        Client->RS: PAYMENT-SIGNATURE {permit2Authorization, witness:{to:UNICA-addr}}
        RS->Fac: /verify   (checks Permit2 allowance; may 412 PERMIT2_ALLOWANCE_REQUIRED first)
        RS->Fac: /settle -> x402ExactPermit2Proxy.settle()
        Fac->Chain: permitWitnessTransferFrom -> wBTC lands at witness.to (UNICA address)
        Chain->Fac: tx confirmed
        RS->UNICA: wBTC received; hand off to UNICA settlement (x402 cannot swap or call pay())
        UNICA->Chain: UNICA's own conversion path, wBTC -> USDC
        UNICA->RS: USDC delivered, order settled
        RS->Client: 200 OK + PAYMENT-RESPONSE + UNICA order receipt
```

**12.4 — Stale-oracle failure (a UNICA-side failure, not an x402 error)**

```
Client  Client->RS: GET /resource + PAYMENT-SIGNATURE (valid x402 authorization)
        RS->Fac: /verify -> isValid:true ; /settle -> success:true (x402 payment settles fine)
        RS->UNICA: hand off received funds for conversion/order-fulfillment
        UNICA->UNICA: price-feed staleness check fails (no x402 error code covers this — §8)
        UNICA->RS: settlement reverts; funds held at the UNICA-controlled address, not lost
        RS->Client: 200 OK is NOT sent; RS reports fulfillment failure + refund/retry instructions
        note: x402's own irreversibility (§7) means the payment leg does not auto-unwind —
              refunding is RS's own transfer back to the payer's address (§7, "how refunds work")
```

**12.5 — Expired quote (x402's own `validBefore` check, before UNICA is ever reached)**

```
Client  Client->RS: GET /resource (old cached PAYMENT-SIGNATURE, validBefore has passed)
        RS->Fac: POST /verify {payload, requirements}
        Fac->Fac: Phase 2 check #4, "Time Window Check" fails
        Fac->RS: {isValid:false, invalidReason:"invalid_exact_evm_payload_authorization_valid_before"}
        RS->Client: 402 + PAYMENT-REQUIRED (fresh accepts[], new validAfter/validBefore window)
        note: UNICA settlement is never invoked — the authorization never became a payment
```

**12.6 — Duplicate / replayed request**

```
Client  Client->RS: GET /resource + PAYMENT-SIGNATURE {id: "pay_abc...", nonce N}
        RS->Fac: /verify -> /settle -> success (first attempt; token contract records nonce N used)
        RS->Client: 200 OK + PAYMENT-RESPONSE
        Client->RS: (retry/replay) same request, same PAYMENT-SIGNATURE
        alt payment-identifier extension in use
            RS->RS: same id "pay_abc...", same payload -> return cached 200 response, no re-settle
        else no extension
            RS->Fac: /settle again -> Chain rejects reused EIP-3009/Permit2 nonce N
            Fac->RS: {success:false, errorReason:"invalid_transaction_state"}
            RS->Client: 402 (no double-spend occurred; the token contract's own nonce check held)
        end
```

**12.7 — Merchant reconciliation**

```
RS      Fac->RS: {success:true, transaction:0x..., network:"eip155:8453", payer:0x...}
        RS->RS: record PAYMENT-RESPONSE.transaction against the UNICA order/quote id
        opt offer-receipt extension in use
            RS->RS: verify signed receipt {network, resourceUrl, payer, issuedAt[, transaction]}
        end
        RS->UNICA: correlate x402 tx hash with UNICA's own settlement receipt/event for the order
        note: base x402 gives only a tx hash + payer; matching it to a specific UNICA order,
              invoice, or merchant ledger row is entirely the resource server's own bookkeeping —
              x402 automates none of it (§7)
```
