# UNICA v4 — Design Review Evidence

**What this file is.** This file records how the UNICA v4 architecture was arrived at, before any of it was
written into this repository: three independent design proposals for the same brief, each anchored to a
scratch prototype built and tested outside this repository purely to measure the proposal's own claims; one
reconciliation that took a base design and layered specific pieces of the other two onto it, decision by
decision, with the losing alternative named each time; and three independent adversarial critique passes over
the reconciled design, each checking its claims against a named primary source. It is an evidence record, not
the specification — it exists so the specification's own claims can be traced back to a measurement or a
critique finding.

**When gathered.** 2026-09-11, prior to any UNICA v4 source file existing under `src/unica-v4/`.

**How gathered.** Three independent design proposals were produced, one per angle — security-first,
deadline-first, and dashboard/data-first — and each was built and run as its own prototype in a scratch
copy kept outside this repository, to turn its sizing, gas and correctness claims into measurements rather
than estimates. This repository itself was only read during that work: nothing was edited, built, or run in it,
and nothing from any prototype was copied into it, per this repository's "Never copy" rule — the eventual
implementation is written fresh from the reconciled design below, not from any prototype's source. A fourth
pass reconciled the three proposals into one design, picking a base and deciding each point of disagreement on
the evidence the three prototypes had produced, and recording what every decision cost and which alternative it
beat. Three further, independent passes then critiqued the reconciled design adversarially — one against the
vendored Uniswap v4 core and hook-base sources, one on deployment mechanics/size/determinism (re-measured
independently in a second scratch build, on disposable local test chains with no RPC to any real network), and
one on whether the design's own test plan actually proves what it claims. No transaction was ever signed or
broadcast to any real chain in the course of this work.

**What this file does NOT establish.**
- It does not say which critique findings were fixed, accepted as a known limitation, or deferred — that
  mapping is the specification's job, not this file's.
- It does not certify anything about a live deployment on chain 46630. No RPC call, no transaction, no explorer
  read was made as part of producing this file.
- Every size, gas, address-determinism and test-count figure below is **measured on a prototype outside the
  repository; implementation re-measures in the repository.** None of it is a measurement of code that exists
  in this repository today, and the actual contracts under `src/unica-v4/` must reproduce every one of these
  numbers independently before they can be relied on.
- It is not a security audit. Each critique lens states its own scope and method; none claims completeness
  beyond what it says it checked.
- A few on-chain facts referenced below (contract addresses, decimals, an existing beacon slot) were read from
  the live chain in earlier, separate work and are carried here as previously reported ("scouted") facts, not
  re-verified as part of gathering this file.

## 1. The three independent angles

Three designs were produced independently and in parallel, each free to solve the brief its own way. Each is
backed by its own scratch prototype, built and tested outside this repository for measurement only.

| Angle | Core bet | What it adds beyond the frozen generation | What it accepts as cost |
|---|---|---|---|
| **SECURITY-FIRST** | Minimize the number of trusted parties and the amount of mutable state; every admin power is listed and bounded; the admin can never move user funds or redirect a settlement. | Each hook pins the exact `PoolKey` and exact opening price it will admit (closing the sibling-pool gap); order creation is permissioned to an admin allowlist (closing the seed-drain path); the hook/executor constructor cycle is broken with an EIP-1153 transient parameter hand-off from the factory. | More moving parts to break the constructor cycle: two calldata blobs, two pinned code-hash immutables, and a transient-storage view that must revert outside a live deployment. |
| **DEADLINE-FIRST** | Keep the frozen experimental hook and executor's settlement logic as-is — it already works and is tested — and change only what per-market generality requires. | Per-market immutables replace the frozen contracts' hardcoded TSLA constants; a factory becomes the only party that deploys and initializes a market; the receipt gains the actual `slot0` fee rates. The hook's constructor deploys its own executor (`CREATE(hook, 1)`), breaking the constructor cycle with no transient hand-off and no dependence on the deployer's nonce. | Order creation stays permissionless, as in the frozen generation, so an allowlist gap (the seed-drain path) is inherited rather than closed. |
| **DASHBOARD/DATA-FIRST** | The registry and per-market executors double as the read surface a future dashboard needs, so a v5 screen can read everything — market discovery, lifecycle state, an exact quote, on-chain orders — through paginated `eth_call` reads with no indexer. | Adds `quote()` (a revert-simulated exact swap quote), on-chain order enumeration, bounded pagination, pool/hook/executor reverse-lookup views, and a `RETIRED` lifecycle state so a mis-listed pair can be replaced. | The extra read surface costs contract-size budget directly: `quote()` alone measured at roughly 1,016 bytes, and the executor prototype ran at 81% of the EIP-170 runtime limit. |

## 2. Reconciliation: one design from three

**The base chosen** was DEADLINE-FIRST's deployment mechanics: it was already built and measured, and it is
the fewest moving parts that meet every requirement. The hook's constructor deploys its own executor, so one
calldata blob is checked against one pinned hash; the factory deploys the registry in a single transaction; and
the factory is the only party that can ever initialize a market's pool.

**Layered on top of that base:**
- From SECURITY-FIRST: the admin-controlled order-creator allowlist (closes the seed-drain path — a stranger
  can still pay an *existing* open order, but the payout goes to the merchant the order names, never to the
  stranger); the exact "perfect tick" rounding flag for the `currency1` opening price (closes a case
  SECURITY-FIRST's own fuzz run found: a tick whose floored square root matches while the true price sits
  fractionally above it); its sender/key-pinning argument for `beforeInitialize`.
- From DASHBOARD/DATA-FIRST: bounded pagination, and the pool/hook/executor reverse-lookup views.

**Dropped entirely:** DASHBOARD/DATA-FIRST's `quote()`, on-chain order enumeration, `RETIRED` lifecycle state
and mutable `setFactory`; SECURITY-FIRST's EIP-1153 constructor-parameter hand-off (the simpler nested-`CREATE`
approach was kept instead).

Re-measured while reconciling (on the deadline-first prototype, now carrying the pieces layered onto it, and
separately against the security-first prototype): sizes matched the deadline-first figures in §1.2 above;
**tests: 31 of 31 passing on the (now-extended) deadline-first prototype, and 9 of 9 on the security-first
one**; a 10-of-10 address-determinism suite confirmed `executor == CREATE(hook, 1)` and `registry ==
CREATE(factory, 1)` hold as designed; and one sabotage demonstration was repeated directly — swapping the
`swapFee` reporting expression for `lpFee` turned both fee-reporting test rows red ("3000 != 3499", "3000 !=
3997"), and restoring it turned them green again.

### 2.1 Named mechanism decisions

**How the hook↔executor constructor cycle is broken.** The frozen pair mined the hook's address against the
executor address predicted at the deployer's next nonce, which needed two transactions signed back-to-back with
nothing else landing in between. SECURITY-FIRST and DASHBOARD/DATA-FIRST both broke that cycle the same other
way — argument-free constructors that read their parameters from the factory's EIP-1153 transient storage
during `createMarket` — and both of those prototypes measured passing (9 of 9, and DASHBOARD/DATA-FIRST's own
27-run suite respectively). That approach was not chosen: it costs two calldata blobs, two pinned code-hash
immutables, an assembly-level or transient-variable hand-off, and a view that must revert outside a live
deployment. The chosen approach — the hook's constructor deploys its own executor by a nested `CREATE` — needs
none of that, at the cost that the executor now takes constructor arguments (which any verification step must
supply) and its address derives from the hook's rather than being salted independently. That loss was judged
harmless because the executor cannot exist at any other address, so the hook's own immutable `EXECUTOR`
reference is the binding that matters.

**Opening-price rounding rule.** DEADLINE-FIRST's original `currency1` rounding rule could retain a tick whose
floored square root equals the target while the exact price sits fractionally above it — a case SECURITY-FIRST's
own fuzz run found in its own first version of the same math and fixed with an explicit "perfect tick" flag.
The reconciliation adopted SECURITY-FIRST's fix; both fuzz suites pass at 10,000 runs. DASHBOARD/DATA-FIRST's
round-to-nearest rule was rejected outright: it can round to a price that pays out *more* per asset than the
configured rate, which breaks the invariant every design otherwise upholds (opening price never exceeds the
configured rate).

**Proving a market is SEEDED.** Three different proofs were on the table: SECURITY-FIRST's position-ledger
proof (owner, exact ticks, and a liquidity floor, re-checked again at activation); DASHBOARD/DATA-FIRST's read
of the official PositionManager's own per-token position info; and "does the pool already have non-zero depth
sitting at the opening tick itself," read directly from the PoolManager's own state. The third was chosen: it
is ordering-independent, simpler, and tests the exact property that matters — that no empty tick range sits
between the opening price and the first available liquidity, which is the defect the frozen generation's live
deployment actually hit. What it gives up: it does not prove *who* owns that depth, and it only proves the
property at one point in time — a seed withdrawn after activation is not re-detected, and settlement is left to
fail safely instead.

### 2.2 The decision log — every reconciliation choice and the option it beat

| # | Decision | What won | What lost, and why | Cost accepted |
|---|---|---|---|---|
| 1 | Market lifecycle has no `RETIRED` state and no pair replacement | SECURITY-FIRST and DEADLINE-FIRST (neither has one) | DASHBOARD/DATA-FIRST's `RETIRED` state and `liveMarketOf` reverse-lookup | A mis-priced market can only be paused, never relisted under the same pair without a new registry (a new release, a new manifest). Reintroducing `RETIRED` would bring back a marketId-reuse and orphaned-executor hazard the reconciliation chose not to accept. |
| 2 | The factory-registry binding is immutable, set once at construction, no `setFactory` | DEADLINE-FIRST / SECURITY-FIRST's immutable binding | DASHBOARD/DATA-FIRST's mutable `setFactory` and its 3-transaction infrastructure bootstrap | None for this release — the binding never needs to change, and it saves two transactions per deployment. |
| 3 | Hook↔executor cycle broken by nested `CREATE`, no transient-storage hand-off | DEADLINE-FIRST's nested `CREATE(hook, 1)` | SECURITY-FIRST's and DASHBOARD/DATA-FIRST's EIP-1153 transient parameter hand-off (both measured passing on their own prototypes) | The executor now takes constructor arguments that verification must supply, and its address derives from the hook's rather than being salted independently (see §2.1). |
| 4 | No `quote()`, no on-chain order enumeration, no running totals | DEADLINE-FIRST / SECURITY-FIRST (neither has them) | DASHBOARD/DATA-FIRST's read surface — `quote()` alone measured about 1,016 bytes of runtime | A dashboard must page `OrderCreated` logs and simulate quotes off-chain (a revert-swap `eth_call`, or a computation from `slot0`); a v5 dashboard's own read needs are explicitly out of scope for this release. |
| 5 | No per-swap `POOL_ID` re-check inside `beforeSwap` | Dropping the check | DEADLINE-FIRST kept one in its own prototype | The check is unreachable in practice — `beforeInitialize` already admits exactly one key for this hook, so the `beforeSwap` copy can never fail and cannot be sabotage-tested. Cost: none. |
| 6 | The opening price is not re-pinned a second time inside the hook itself | The factory as sole initializer, using its own stored price, with the returned tick checked once | SECURITY-FIRST's belt-and-suspenders pin inside the hook's `beforeInitialize` | A factory defect could in principle initialize at a wrong price; mitigated by the design's own readback check that `slot0.sqrtPriceX96` equals the stored `initSqrtPriceX96` after every initialize call. |
| 7 | SEEDED is proven once, from pool depth at the opening tick — see §2.1 | The PoolManager-state proof | SECURITY-FIRST's position-ledger ownership proof, re-checked at activation (SECURITY-FIRST's own unpause does not re-verify the seed) | SEEDED does not establish who owns the depth, and is a point-in-time proof only; a seed withdrawn after activation is not re-detected, and settlement instead fails safely until the admin notices and pauses. |
| 8 | The seed's tick range is not stored on-chain | Computing it in a shared library used by the script and the tests | Storing the designed range in the registry | A dashboard cannot read the *designed* range from the registry, only the realized depth once seeded. |
| 9 | No upper bound on how far in the future an order's deadline may be set | Dropping the bound | SECURITY-FIRST's 7-day maximum order window | An allowlisted creator could create a very long-lived order; bounded in practice by the creator allowlist itself and by the admin's ability to pause. |
| 10 | Single EOA admin, two-step transfer; no separate pause guardian, multisig or timelock | The simpler single-key model | A guardian/multisig/timelock role, considered and not adopted for this release | One compromised key controls listing and liveness — but never user funds, since the admin holds none. |
| 11 | The settlement receipt carries fee **rates** only, no fee **amounts** | Rates only | Carrying computed amounts in the receipt | Consumers must compute `amountIn * swapFeePips / 1e6` themselves rather than reading it directly. |
| 12 | No dynamic-fee pools; no liquidity or donate hook flags | Static fee, no extra flags | Adding those flags to gate liquidity changes | Third parties may add or remove their own liquidity freely; harmless to payers, but it means seed depth is only proven at one point in time, not continuously. |
| 13 | No Permit2 or signature-based payment on the payer side | Approve-then-pay, as inherited from the frozen generation | A Permit2 or signature path | The payer sends two transactions per payment instead of one. |
| 14 | The deploy wrapper takes the rate as a raw `1e18`-scaled integer | Raw integers in the config file | DEADLINE-FIRST's human-decimal-to-integer conversion inside the wrapper | The owner writes scaled integers directly; the script prints the human-readable form back for confirmation. |
| 15 | No retries, multicall, or cross-market approval batching | Repeating the frozen sequence per market | Batching seed transactions across markets | Four seed transactions per market repeat the frozen pattern, keeping each deployment stage self-contained and independently resumable. |
| 16 | No upgradeability and no admin-renounce path | Fixed, non-upgradeable contracts | Adding an upgrade path | A bug fix requires a new deployment, not a patch. |

If the work fell behind schedule, the reconciliation recorded its own fallback cut order in advance: drop two
named fork rows first, then two named invariant checks, then reduce the decimals matrix to the six {6, 18}
combinations — and named a short list of checks (the fee-reporting rows, several of the payer-protection rows, and the
ordering rows) that were never to be dropped regardless of time pressure. That schedule-pressure ordering is
recorded here because it was part of the reconciliation's own decision-making, not because this file asserts
anything about which cuts were actually taken.

## 3. Adversarial critique of the reconciled design

### Critique findings, by lens

Three independent adversarial passes checked the reconciled design above. Each pass names its own scope and method; none of the three re-ran the prototypes or touched the live chain. The findings are listed exactly as raised — this file does not say which were fixed, dropped, or accepted; that mapping belongs to the specification.

#### Lens A — Uniswap v4 Hook Security

**Scope.** Checked the reconciled design's hook-security claims against the vendored `lib/uniswap-hooks/lib/v4-core` sources compiled by this repository's own remappings (confirmed byte-identical to the `v4-periphery` copy), against `lib/uniswap-hooks/src/base/BaseHook.sol`, against the frozen `experimental` sources, and against the deadline-first prototype. Nothing was run inside this repository; arithmetic and topic-hash checks were done offline, outside the repository, with no RPC call. **Verdict on the core guarantees.** Sender semantics, exact-key binding, executor-only swaps, the fee formula, pause atomicity and delta accounting all hold against the source. The findings below are one overstated security claim, several overstated or unobservable statements, and test gaps where a property holds today but nothing pins it.
