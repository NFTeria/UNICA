# The v4 troubleshooting page pairs error names with hex selectors and gives no cause or fix

## Affected official repository and version

`github.com/Uniswap/docs`, `content/protocols/v4/guides/troubleshooting.mdx`, commit
`1c7597d73be0e9a3a4e44aa75b8fb212b40ea136` (main, read 2026-09-05T16:47:14Z).

## Exact reproduction

Re-run today, 2026-09-05:

```
$ gh api repos/Uniswap/docs/contents/content/protocols/v4/guides/troubleshooting.mdx \
    --jq '.content' | base64 -d > troubleshooting_check.txt
$ wc -l troubleshooting_check.txt
101 troubleshooting_check.txt
$ grep -n "CurrencyNotSettled\|HookAddressNotValid" troubleshooting_check.txt
15:| `IPoolManager.CurrencyNotSettled.selector`          | `0x5212cba1` |
30:| `Hooks.HookAddressNotValid.selector`                | `0xe65af6a0` |
```

Both rows are unchanged from the 2026-09-04 pass: table entries only, no prose column on
either row, matching the "ten `IPoolManager` errors, four `Hooks.sol` errors, eleven
`Pool.sol` errors — zero causes, zero reproductions, zero fixes" characterization already
recorded in this project's own spec notes.

## Expected behaviour

A developer who arrives at this page with a hex selector from a failed transaction
(`0xe65af6a0`, `0x5212cba1`) learns the cause and the fix.

## Actual behaviour

The page names the identifier and the selector and stops. It answers "what is this error
called" but not "why did it fire" or "what do I change."

## Minimal command or test

```sh
gh api repos/Uniswap/docs/contents/content/protocols/v4/guides/troubleshooting.mdx \
  --jq '.content' | base64 -d | grep -n "CurrencyNotSettled\|HookAddressNotValid"
```

## Impact

The page is reachable specifically by someone debugging a live failure, which is exactly
the moment a bare identifier-to-selector lookup is least useful — the reader already knows
the name from the revert reason; what they lack is the cause.

## Proposed correction

Additive rows for the two errors a hook author is most likely to hit, phrased from this
project's own first-hand cause analysis: `HookAddressNotValid` — the mined low bits do not
match the hook's declared permission flags, most often because the deployer address changed
after mining (a `CREATE2` salt is bound to the deploying address); `CurrencyNotSettled` — a
settlement path completed without calling `sync` while a different currency was left synced
from an earlier leg of the same unlock. The existing selector table is left untouched;
these are new rows.

## Evidence generated by UNICA (file:line in this repository)

`specs/HOOK-SPEC.md:491-492` — the raw notes naming both selectors and this exact proposed
correction ("one cause + one reproduction line per selector. We will ship tests that
deliberately reproduce both and can contribute the text"). `HookAddressNotValid`:
`test/V4SettlementHook.t.sol:61` (`test_RevertWhen_AddressBitsSayBeforeSwapOnly`), `:67`
(`test_RevertWhen_AddressBitsSayAfterSwapOnly`) — exactly the mined-bits-versus-declared-flags
revert. `CurrencyNotSettled` / its native-settlement cause: `test/I7NativeSettle.t.sol:69`
(`test_I7_DefenceOff_ForeignSync_Reverts`, the failing case) and `:99`
(`test_I7_DefenceOn_ForeignSync_Survives`, the fix). Every proposed row is backed by a
public, passing test in this repository.

## Classification

documentation ambiguity — the selectors listed are correct; what is missing is the cause
and fix prose the page's own purpose (troubleshooting) implies it should carry.
