# `PoolManager.sol`'s exact `pragma solidity 0.8.26;` splits an unpinned downstream build across two compiler versions

## Affected official repository and version

`github.com/Uniswap/v4-core`, `src/PoolManager.sol:2` (`pragma solidity 0.8.26;`), pinned
commit `d153b048868a60c2403a3ef5b2301bb247884d46` (the commit this repository's
`lib/uniswap-hooks/lib/v4-core` submodule carries).

## Exact reproduction

Run fresh today, 2026-09-05, in a scratch project outside this repository
(`/private/tmp/.../scratchpad/day6/E/repro/two-compiler-split`), remapped into the pinned
`v4-core` above, `foundry.toml` with no `solc_version` set:

`src/Wrap.sol` (imports `PoolManager`, `pragma solidity ^0.8.24;`), `src/MyContract.sol`
(no `v4-core` dependency, `pragma solidity ^0.8.28;`):

```
$ forge build
Compiling 46 files with Solc 0.8.26
Compiling 1 files with Solc 0.8.30
Solc 0.8.30 finished in 45.45ms
Solc 0.8.26 finished in 339.73ms
Compiler run successful!

$ python3 -c "import json; print(json.load(open('out/MyContract.sol/MyContract.json'))['metadata']['compiler']['version'])"
0.8.30+commit.73712a01
$ python3 -c "import json; print(json.load(open('out/PoolManager.sol/PoolManager.json'))['metadata']['compiler']['version'])"
0.8.26+commit.8a97fa7a
```

Toolchain: `forge 1.3.5-foundry-zksync-v0.1.9`. Control run: the same project with
`MyContract.sol` at `pragma solidity ^0.8.24;` instead of `^0.8.28;` folds into a single
`Compiling 47 files with Solc 0.8.26` run — no split, because 0.8.26 satisfies `^0.8.24`.
The split appears specifically when a sibling file's floor version excludes 0.8.26.

## Expected behaviour

A downstream Foundry project that imports `PoolManager` and sets no `solc_version` of its
own compiles with one compiler for the whole project, or is told clearly that it will not.

## Actual behaviour

`forge` silently and correctly (by its own auto-detection design) compiles the
`PoolManager`-reaching files at exactly `0.8.26` and every other file at whatever higher
version its own pragma floor demands — in this case `0.8.30`, auto-installed. Nothing in
`v4-core`'s README, NatSpec, or `foundry.toml` says this is a consequence of the exact
pragma, so a project that later needs one compiler for verification (a single artifact,
one compiler version) discovers the split only when explorer verification fails or when a
size/gas discrepancy between test and production builds is chased down by hand.

## Minimal command or test

```sh
mkdir scratch && cd scratch
# remappings.txt: @uniswap/v4-core/=<pinned v4-core>/, solmate/=<pinned v4-core>/lib/solmate/,
#                 forge-std/=<pinned v4-core>/lib/forge-std/src/
# foundry.toml: [profile.default] src="src" out="out" libs=["lib"]   (no solc_version)
# src/Wrap.sol:        pragma solidity ^0.8.24; imports PoolManager
# src/MyContract.sol:  pragma solidity ^0.8.28; no v4-core dependency
forge build   # → two "Compiling N files with Solc X.Y.Z" lines, two solc versions
```

## Impact

Any downstream project that (a) imports `PoolManager` directly rather than etching its
deployed bytecode, and (b) writes any of its own contracts against a pragma floor above
0.8.26 (an ordinary choice — later Solidity releases add features some projects want), and
(c) does not explicitly pin `solc_version`, ends up with two different compiler versions
producing artifacts in the same `out/` directory without any error or warning. The failure
surfaces downstream and late: at `forge verify-contract` time, when the deployed bytecode
must match one specific compiler exactly, or when a `--sizes` or gas comparison across
files silently spans two toolchains.

## Proposed correction

No code change requested. An issue asking two things: whether the exact (non-caret) pragma
on the deployed singleton is intended to also govern every downstream compilation unit
that merely imports the source, and whether the test-facing surface could instead pin a
caret range so downstream projects are not forced onto 0.8.26 for every file that touches
`PoolManager`. Alternatively, a two-sentence README note stating the consequence plainly,
so an integrator can decide to pin `solc_version` before hitting it instead of after.

## Evidence generated by UNICA (file:line in this repository)

`foundry.toml:12-16` — the comment block explaining the mitigation this project adopted:
pin `solc_version = "0.8.30"` and etch the official `PoolManager` runtime from hookmate's
artifact (`test/utils/SettlementTestBase.sol:18-19`, `:82-91`) rather than compiling
`v4-core`'s source, so nothing in the tree needs `0.8.26` and one compiler serves tests,
scripts and verification. The hook built and verified this way is live on Sepolia at
`0x23b46783709E4A94C229612bfA55580a6682c040` (Exact Match, compiler v0.8.30+commit.73712a01,
per the explorer). Today's scratch reproduction (this file, above) is the first isolated,
minimal confirmation of the mechanism itself — `docs/INTEGRATIONS.md` rank 7 (2026-09-04)
recorded the on-chain day-1 incident but explicitly stated "the split was not re-created in
a fresh minimal project this pass"; that gap is closed by today's run, and the corresponding
FEEDBACK.md entry (`FEEDBACK-ENTRIES.md`, 2026-09-05) is the dated first-hand record of it.

## Classification

documentation ambiguity — the compiler behaviour itself (per-file solc auto-detection) is
Foundry working as designed; what is missing is any statement from `v4-core` that its exact
pragma has this downstream consequence, which is what turns a design choice into a trap for
integrators who do not already know to look for it.
